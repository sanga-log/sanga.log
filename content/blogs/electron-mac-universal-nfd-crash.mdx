## 칩마다 설치 파일이 따로 있었습니다

'김캐디 사장님'(이하 사장님앱)은 Electron으로 만든 매장 관리 데스크톱 앱입니다. 매장 PC는 대부분 Windows이고, Mac을 쓰는 매장은 두세 곳뿐입니다. 그래서 Mac 설치 파일은 미리 준비해 둔 게 아니라, 사장님이 필요하다고 하실 때마다 그때그때 대응해 왔습니다. 처음에는 한두 곳을 위해 Intel 칩(x64)용을 만들었는데, 나중에 요청이 또 들어왔던 매장은 칩이 달라서 M 칩(arm64)용을 하나 더 만들게 되었습니다. 그렇게 칩에 따라 설치 파일이 나뉘었고, 빌드할 때마다 배포를 두 번씩 해야 했습니다.

이걸 한 번으로 줄이려고, 이번에 두 설치 파일을 universal 빌드로 합쳤습니다. package.json의 맥 빌드 스크립트에서 electron-builder에 `--mac --universal`을 붙이면, 두 칩용 앱을 각각 만든 뒤 하나로 묶어 줍니다. 옵션 하나만 더하면 끝날 줄 알았는데, 그렇지 않았습니다.

빌드 전에 손볼 게 두 가지 있었습니다. 앱은 외부 시스템과 연동할 때 Chromium을 띄우는데, Chromium도 칩마다 실행 파일이 따로 있어서 실행 중인 맥의 칩에 맞는 쪽을 고릅니다. 그동안은 설치 파일을 칩별로 만들면서 그 칩용 Chromium 하나만 넣었기 때문에, 앱에 함께 넣는 파일 목록(`extraResources`)에는 마지막으로 만든 M 칩용만 남아 있었습니다. universal 앱에는 둘 다 있어야 해서 Intel 칩용을 채웠습니다. 그리고 병합 도구(`@electron/universal`)는 두 앱의 실행 파일을 짝지어 하나로 합치는데, 두 앱에 똑같이 들어 있는 실행 파일을 만나면 멈춥니다. 두 Chromium이 여기서 걸리기 때문에, 합치지 않고 각각 그대로 두도록 예외로 지정했습니다.

```json
"x64ArchFiles": "Contents/Resources/public/chrome-mac-*/**"
```

## 빌드가 세 번 막혔습니다

준비를 마치고 빌드를 돌리자, 그때부터 하나씩 막혔습니다.

### 1. pattern is too long

```
⨯ pattern is too long  failedTask=build
TypeError: pattern is too long
```

원인은 `react-native` 패키지였습니다. 예전에 styled-components의 타입 패키지를 설치하면서 함께 딸려 들어온 것으로 확인됐는데, 정작 코드 어디에서도 import하지 않는 패키지였습니다. 이 패키지에 실행 파일이 들어 있어서 electron-builder가 파일 3,514개를 통째로 asar 밖에 풀어 두었고, 병합 도구가 이 목록을 패턴 하나로 이어 붙이다가 길이 제한에 걸렸습니다.

이 단계는 칩별 앱에 하나씩 든 `app.asar`(앱 코드를 묶은 파일)를 하나로 합치는 과정입니다. `mergeASARs: false`로 이 합치기를 끄면 에러는 사라지지만, `app.asar` 두 개를 그대로 넣어 두는 거라 그만큼 앱 크기가 커집니다. 쓰지 않는 패키지 때문에 앱 용량을 키울 이유는 전혀 없었습니다. 합치기는 그대로 두고 맥 빌드에 넣는 파일 목록에서 `react-native`를 뺐고, 에러도 바로 해결할 수 있었습니다.

### 2. git은 무시하는 폴더를 electron-builder는 봅니다

```
⨯ ENOENT: no such file or directory, open '.../.claude/worktrees/<이름>/.qa-session'
```

프로젝트 안에는 AI 에이전트가 작업할 때 쓰는 프로젝트 사본이 여러 개 쌓여 있었습니다. 사본마다 `node_modules`가 따로 들어 있어서 용량도 컸습니다. git 제외 목록에 들어 있어서 신경 쓴 적이 없었는데, electron-builder는 그 목록을 보지 않습니다. 이 사본들까지 통째로 포장하려다가, 그 사이 사라진 파일을 못 찾고 실패한 거였습니다.

Mac과 Windows 설정 양쪽에 `!.claude/**`를 넣었습니다.

### 3. pkg는 한글 경로에서 막혔습니다

```
pkgbuild: error: Cannot write package to "...".
(The file "package.bom" couldn't be saved in the folder ...
```

dmg까지는 만들어졌는데, 이어서 pkg를 만드는 `pkgbuild`가 한글 이름이 들어간 헬퍼 앱 경로에서 실패했습니다. 단일 칩 버전으로 빌드해도 똑같은 에러가 나서, universal 때문은 아니라고 판단했습니다.

pkg는 빌드 설정에 들어만 있었고 배포에는 사용하지 않았습니다. 사장님들이 다운로드 메뉴에서 받아 가시던 맥 설치 파일은 zip이었기 때문에, 쓰지 않는 pkg는 빌드 설정에서 빼고 빌드를 이어 갔습니다.

## 앱이 0.45초 만에 꺼졌습니다

세 번의 실패 끝에 드디어 빌드가 끝까지 돌았습니다. 빌드 성공과 정상 실행은 별개이기에, 홈페이지에서 설치 파일을 내려받는 과정부터 사장님들이 설치하시는 순서를 그대로 따라 하나씩 테스트해 보았습니다.

받은 dmg를 열어 앱을 응용 프로그램(`/Applications`) 폴더로 끌어다 놓은 뒤 실행해 봤는데, 0.45초쯤 떠 있다가 곧바로 꺼져 버렸고, 화면에는 아래와 같은 크래시 리포트 창만 남았습니다.

```
Exception Type:  EXC_BREAKPOINT (SIGTRAP)
Termination Reason:  Namespace SIGNAL, Code 5, Trace/BPT trap: 5
Thread 0 Crashed:: CrBrowserMain
```

이상하게도 빌드 폴더에 생긴 앱을 실행하면 정상적으로 열렸는데, `/Applications`에 Finder로 끌어다 놓은 앱만 계속 꺼졌습니다.

설치 파일 종류도 바꿔 봤습니다. 같은 앱이라도 zip을 아카이브 유틸리티로 풀면 정상이고, dmg에서 Finder로 끌어다 놓으면 꺼졌습니다. 이전 배포는 zip이었으니, dmg로 바꾸면서 새로 생긴 문제였습니다.

다시 zip 배포로 돌아가면 당장 문제는 피할 수 있었습니다. 하지만 이왕 설치 방식을 바꾸는 김에, 사장님이 압축을 직접 풀 필요 없이 다른 맥 앱들처럼 dmg를 열어 앱을 응용 프로그램 폴더로 끌어다 놓기만 하면 설치가 끝나게 하고 싶었습니다. 우회하는 대신 원인을 끝까지 찾아 dmg로 배포하기로 결정했습니다.

### 이름의 바이트가 달랐습니다

정상 앱과 꺼지는 앱은 겉으로는 다른 데가 없었고, 파일 이름도 화면에서는 똑같았습니다. 하지만 한글은 같은 글자를 NFC와 NFD라는 두 가지 형식으로 저장할 수 있고, 형식에 따라 저장되는 바이트가 다릅니다. 그래서 두 앱의 이름을 글자가 아닌 바이트로 비교해 봤습니다.

| 형식 | "사"를 저장하는 방식 | UTF-8 바이트 |
|---|---|---|
| NFC (합쳐진 글자) | U+C0AC | `EC 82 AC` |
| NFD (풀어 쓴 자모) | U+1109, U+1161 | `E1 84 89 E1 85 A1` |

바이트를 찍어 보니 빌드 폴더의 앱은 NFC, `/Applications`의 앱은 NFD였습니다. 그런데 빌드 폴더의 앱을 복사해 안쪽 이름까지 전부 NFD로 바꾼 사본은 멀쩡히 실행되는 걸 보니, NFD 자체가 범인은 아니었습니다.

### 파일을 하나씩 맞바꿔 봤습니다

먼저 정상 앱과 꺼지는 앱의 파일을 하나씩 서로 바꿔 넣어 봤습니다. 파일 하나를 바꿔 넣었을 때 정상이던 앱이 꺼지거나 꺼지던 앱이 정상으로 뜨면, 그 파일이 원인인 셈입니다. 이렇게 범위를 좁혀 가니, 결과를 가르는 건 헬퍼 앱(사장님앱 Helper (GPU).app - Electron이 그래픽 처리를 맡기는 보조 앱) 안 `MacOS` 폴더에 든 실행 파일 `사장님앱 Helper (GPU)` 하나였습니다. 같은 헬퍼 앱 안에 있는 `Info.plist`와 `PkgInfo`(앱 정보를 적어 두는 파일)는 바꿔 넣어도 결과가 그대로였습니다.

다음으로 이 파일의 내용과 이름 중 무엇이 원인인지 가렸습니다. 이 실행 파일이 든 헬퍼 폴더 이름은 두 앱 모두 NFC였고, 실행 파일 이름은 정상 앱이 NFC, 꺼지던 앱이 NFD였습니다. 그래서 정상 앱의 파일에는 NFD 이름을, 꺼지던 앱의 파일에는 NFC 이름을 붙여 실행해 봤습니다.

| 파일 내용 | 폴더 이름 | 파일 이름 | 결과 |
|---|---|---|---|
| 정상 앱의 파일 | NFC | NFD | 꺼짐 |
| 꺼지던 앱의 파일 | NFC | NFC | 정상 |

파일 내용이 아니라 이름 형식이 원인이었습니다. 폴더와 형식이 다른 이름을 붙이면 정상 파일도 꺼졌고, 같은 형식으로 맞추면 꺼지던 파일도 정상으로 떴습니다.

### 폴더와 파일의 형식이 섞여 있었습니다

마지막으로 이 이름이 어떻게 어긋나 있는지 봤습니다. Finder로 끌어다 놓은 앱의 이름을 위치별로 찍어 보면 형식이 제각각입니다. 이렇게 섞여 있으면 꺼지는데, 빌드 폴더의 앱이나 zip으로 푼 앱은 원래 형식이 유지돼 섞일 일이 없었기 때문에 꺼지지 않았던 겁니다.

| 위치 | 형식 |
|---|---|
| 최상위 폴더 `사장님앱.app` | NFD |
| 본체 실행 파일 `Contents/MacOS/사장님앱` | NFD |
| 헬퍼 폴더 `사장님앱 Helper (GPU).app` | **NFC** |
| 그 안의 실행 파일 `사장님앱 Helper (GPU)` | NFD |

### 앱 안쪽 이름만 영문으로 바꿨습니다

설치하면서 한글 이름의 형식이 섞여 버리는 게 문제였기 때문에, 앱 안쪽에서는 한글 이름을 아예 없애기로 했습니다. 영문은 NFC로 저장하든 NFD로 저장하든 바이트가 똑같아서, 어떻게 옮겨도 형식이 섞일 일이 없습니다.

다만 바깥 `.app` 폴더 이름은 한글로 남겼습니다. 사장님이 응용 프로그램 폴더에서 보는 이름이 바로 이 폴더 이름이라 바꾸고 싶지 않았고, 안쪽 이름만 영문으로 바꿔도 크래시는 사라졌습니다. 바꾼 이름과 그대로 둔 이름은 이렇습니다.

| 이름 | 바꾸기 전 | 바꾼 뒤 |
| --- | --- | --- |
| 앱 폴더 | 사장님앱.app | 그대로 |
| 본체 실행 파일 | 사장님앱 | OwnerApp |
| 헬퍼 앱 폴더 4개 | 사장님앱 Helper (GPU).app 등 | OwnerApp Helper (GPU).app 등 |
| 헬퍼 실행 파일 4개 | 사장님앱 Helper (GPU) 등 | OwnerApp Helper (GPU) 등 |
| Info.plist 5개의 실행 파일 이름·앱 이름 | 사장님앱, 사장님앱 Helper (GPU) 등 | OwnerApp, OwnerApp Helper (GPU) 등 |
| Info.plist 5개의 표시 이름 | 사장님앱, 사장님앱 Helper (GPU) 등 | 그대로 |

이름을 바꾸는 작업은 패키징 직후에 도는 electron-builder의 `afterPack` 훅에 넣었습니다.

```js
// scripts/afterPack.js (이름은 바꿔 적었습니다)
const ASCII_NAME = "OwnerApp";

exports.default = async function afterPack(context) {
  if (context.electronPlatformName !== "darwin") return;

  const productFilename = context.packager.appInfo.productFilename;
  const contents = path.join(context.appOutDir, `${productFilename}.app`, "Contents");
  const macOSDir = path.join(contents, "MacOS");
  if (fs.existsSync(path.join(macOSDir, ASCII_NAME))) return;

  fs.renameSync(path.join(macOSDir, productFilename), path.join(macOSDir, ASCII_NAME));
  setPlist(path.join(contents, "Info.plist"), "CFBundleExecutable", ASCII_NAME);
  setPlist(path.join(contents, "Info.plist"), "CFBundleName", ASCII_NAME);

  // 헬퍼 앱 4개도 실행 파일, 폴더, Info.plist를 같은 방식으로 바꿉니다
};
```

universal 옵션으로 빌드할 때 electron-builder는 Intel 칩(x64)용과 M 칩(arm64)용 앱을 각각 패키징한 뒤, 마지막에 둘을 하나로 합칩니다. 이때 `afterPack` 훅은 각 칩별 패키징 시점과 최종 병합 시점까지 총 세 번 호출됩니다. 마지막 호출은 합친 앱을 서명하기 전에 한 번 더 손볼 수 있게 electron-builder가 넣어 둔 것입니다.

내부 파일 이름을 영문으로 바꾸는 로직은 앞선 두 번의 패키징 단계에서 이미 실행됩니다. 따라서 최종 병합 단계에서는 영문 실행 파일이 보이면 작업을 건너뛰도록 했습니다. 이 확인이 없으면 이미 영문으로 바뀌어 없어진 한글 파일을 찾으려다 빌드가 실패합니다.

처음엔 실행 파일과 헬퍼 폴더의 이름만 바꿨는데, 설치한 앱은 여전히 꺼졌습니다. `Info.plist`에 적힌 앱 이름(`CFBundleName`)이 아직 한글로 남아 있었기 때문입니다. 이것까지 영문으로 바꾸자 드디어 앱이 정상적으로 실행됐습니다.

## 이번엔 1.30GB가 됐습니다

크래시를 잡고 나니 이번엔 용량이 문제였습니다. dmg가 1.30GB, 설치하면 3.1GB였습니다. 원래 칩별 zip은 220MB 정도였는데, 앱 코드를 묶은 `app.asar` 하나가 2.2GB나 됐습니다.

원인은 Chromium 폴더를 CRA의 `public/` 폴더에 넣어 둔 구조였습니다. 이 때문에 빌드할 때마다 Chromium이 두 경로로 복사되고 있었습니다.

```
public/  Chromium 원본 (맥 2개, 윈도우 1개)
│
├─ ① CRA 빌드: public/ 전체를 build/로 복사
│     └─ electron-builder: build/를 app.asar에 묶음
│           → asar 안의 사본: 아무도 실행하지 않음
│
└─ ② extraResources: 맥용 2개만 asar 바깥 Resources/public/으로 복사
        → asar 바깥의 사본: 앱이 실제로 실행함
```

앱 코드는 ②번 경로에 있는 Chromium만 실행합니다. ①번 경로로 `app.asar`에 들어간 사본은 쓰이지도 않으면서 용량만 차지하고 있었고, 맥 빌드인데도 윈도우용까지 함께 들어 있었습니다.

게다가 ①번 사본은 원본보다 세 배 가까이 컸습니다. CRA는 `public/`을 `build/`로 복사할 때 심볼릭 링크를 실제 파일로 풀어서 복사합니다(`dereference: true`). 맥용 Chromium 안에는 같은 내용을 가리키는 링크가 5개씩 있어서, `build/`에는 링크 대신 같은 파일이 세 벌씩 들어갔습니다.

| Chromium | `public/` 원본 | `build/` 사본 |
|---|---|---|
| 맥 M 칩용 | 289MB | 865MB |
| 맥 Intel 칩용 | 309MB | 924MB |
| 윈도우용 (링크 없음) | 276MB | 276MB |

그래서 ①번 경로에서만 Chromium을 빼는 제외 규칙을 넣었습니다. 처음엔 맥 설정인 `mac.files`에 넣었는데 `build/` 경로에는 먹히지 않았고, 최상위 `build.files`로 옮기고 나서야 빠졌습니다.

```json
"build": {
  "files": [
    "!build/chrome-mac-arm/**",
    "!build/chrome-mac-intel/**",
    "!build/chrome-win/**"
  ]
}
```

이 규칙은 사본을 한 번 지우고 끝나는 게 아니라, 빌드할 때마다 ①번 사본을 걸러 내는 필터입니다. CRA가 빌드마다 `public/`을 다시 복사하기 때문에, 이 규칙이 빠지면 설치 파일은 다시 커집니다.

다만 이 규칙은 생긴 사본을 걸러 낼 뿐, 사본이 생기는 원인은 그대로 남아 있습니다. `public/`은 웹 페이지와 함께 나갈 파일을 두는 폴더인데, 앱이 실행할 프로그램인 Chromium을 여기에 둔 것이 시작이었습니다. 그래서 Chromium을 `public/` 밖의 별도 폴더로 옮기고, `extraResources`가 그 폴더에서 복사해 오도록 고칠 계획입니다. 이렇게 하면 CRA가 Chromium을 아예 복사하지 않으니 제외 규칙도 필요 없어집니다.

## 결과

| 항목 | 이전 (칩별 zip) | universal, 중복 제거 전 | 최종 |
|---|---|---|---|
| 설치 파일 | 2개 | 1개 | 1개 |
| 다운로드 크기 | 212MB, 227MB | 1.30GB | 546MB |
| 설치 후 용량 | 측정 안 함 | 3.1GB | 약 1.4GB |

1.30GB에서 546MB로 58% 줄었지만, 이번 전환으로 불어난 만큼을 덜어 낸 것일 뿐입니다. 이전 칩별 zip과 비교하면 다운로드는 약 2.5배 커졌습니다. 칩 두 벌을 담았으니까요.

대신 이제는 사장님께 맥 칩이 무엇인지 여쭤보지 않아도 됩니다. 어떤 칩의 맥이든 설치 파일 하나로 설치되고, 다운로드 메뉴에도 맥은 하나만 남아 칩을 고를 필요가 없습니다. 빌드할 때마다 두 번 하던 배포도 한 번으로 줄었습니다.

## 마무리

평소에도 사장님 입장에서 겪을 수 있는 경우를 생각하며 테스트해 왔지만, 이번 일로 왜 그렇게 해야 하는지 다시 한번 느꼈습니다. 빌드가 끝나면 로컬에 생긴 앱을 바로 실행해 보고, 이상이 없으면 넘어가는 경우도 있습니다. 이번 크래시는 다운로드부터 설치까지 제대로 되는지 보려고, 사장님처럼 처음부터 하나씩 따라 해보다가 발견하게 된 경우입니다. dmg를 열어 Finder로 옮기고 실행해 보지 않았다면, 알아채지도 못한 채 그대로 운영에 배포했을 겁니다. 개발만 하고 끝이 아니라, 실제로 쓰는 환경에서 잘 돌아가는지 직접 확인하는 것까지 개발자의 몫입니다.
