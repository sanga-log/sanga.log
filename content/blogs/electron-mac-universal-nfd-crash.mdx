## 칩마다 설치 파일이 따로 있었습니다

'김캐디 사장님'(이하 사장님앱)은 Electron으로 만든 매장 관리 데스크톱 앱입니다. 매장 PC는 대부분 Windows이고, Mac을 쓰는 매장은 두세 곳뿐입니다. 그래서 Mac 설치 파일은 미리 준비해 둔 게 아니라, 사장님이 필요하다고 하실 때마다 그때그때 대응해 왔습니다. 처음에는 한두 곳을 위해 Intel 칩(x64)용을 만들었는데, 나중에 요청이 또 들어왔던 매장은 칩이 달라서 M 칩(arm64)용을 하나 더 만들게 되었습니다. 그렇게 칩에 따라 설치 파일이 나뉘었고, 빌드할 때마다 배포를 두 번씩 해야 했습니다.

이걸 한 번으로 줄이려고, 이번에 두 설치 파일을 universal 빌드로 합쳤습니다. package.json의 맥 빌드 스크립트에서 electron-builder에 `--mac --universal`을 붙이면, 두 칩용 앱을 각각 만든 뒤 하나로 묶어 줍니다. 옵션 하나만 더하면 끝날 줄 알았는데, 그렇지 않았습니다.

빌드 전에 손볼 게 두 가지 있었습니다. 앱은 외부 시스템과 연동할 때 Chromium을 띄우는데, Chromium도 칩마다 실행 파일이 따로 있어서 실행 중인 맥의 칩에 맞는 쪽을 고릅니다. 그동안은 설치 파일을 칩별로 만들면서 그 칩용 Chromium 하나만 넣었기 때문에, 앱에 함께 넣는 파일 목록(`extraResources`)에는 마지막으로 만든 arm용만 남아 있었습니다. universal 앱에는 둘 다 있어야 해서 intel용을 채웠습니다. 그리고 병합 도구(`@electron/universal`)는 두 앱의 실행 파일을 짝지어 하나로 합치는데, 두 앱에 똑같이 들어 있는 실행 파일을 만나면 멈춥니다. 두 Chromium이 여기서 걸리기 때문에, 합치지 않고 각각 그대로 두도록 예외로 지정했습니다.

```json
"x64ArchFiles": "Contents/Resources/public/chrome-mac-*/**"
```

## 빌드가 세 번 막혔습니다

준비를 마치고 빌드를 돌리자, 그때부터 하나씩 막혔습니다.

### 1. pattern is too long

```
⨯ pattern is too long  failedTask=build
TypeError: pattern is too long
```

원인은 `react-native` 패키지였습니다. 처음에는 styled-components의 타입 패키지(`@types/styled-components`)가 `@types/react-native`를 거쳐 딸려 들어왔고, 2024년 초에는 package.json에 직접 추가되어 그대로 남아 있었습니다. 앱 코드에서는 어디에서도 import하지 않는 패키지였습니다. 이 패키지에 실행 파일이 들어 있어서 electron-builder가 파일 3,514개를 통째로 asar 밖에 풀어 두었고, 병합 도구가 이 목록을 패턴 하나로 이어 붙이다가 길이 제한에 걸렸습니다.

이 단계는 칩별 앱에 하나씩 든 `app.asar`(앱 코드를 묶은 파일)를 하나로 합치는 과정입니다. `mergeASARs: false`로 이 합치기를 끄면 에러는 사라집니다. 대신 `app.asar` 두 개를 그대로 넣어 두고 실행할 때 칩에 맞는 쪽을 쓰게 되어, 그만큼 앱이 커집니다. 쓰지 않는 패키지 때문에 앱을 키울 이유는 없었습니다. 그래서 합치기는 그대로 두고, 맥 빌드에 넣는 파일 목록에서 `react-native`를 바로 뺐습니다. 이 에러는 그걸로 해결됐습니다.

### 2. git은 무시하는 폴더를 electron-builder는 봅니다

```
⨯ ENOENT: no such file or directory, open '.../.claude/worktrees/<이름>/.qa-session'
```

프로젝트 안에는 AI 에이전트가 작업할 때 쓰는 프로젝트 사본이 여러 개 쌓여 있었습니다. 사본마다 `node_modules`가 따로 들어 있어서 용량도 컸습니다. git 제외 목록에 들어 있어서 신경 쓴 적이 없었는데, electron-builder는 그 목록을 보지 않습니다. 이 사본들까지 통째로 포장하려다가, 그 사이 사라진 파일을 못 찾고 실패한 거였습니다.

맥과 윈도우 설정 양쪽에 `!.claude/**`를 넣었습니다.

### 3. pkg는 한글 경로에서 막혔습니다

```
pkgbuild: error: Cannot write package to "...".
(The file "package.bom" couldn't be saved in the folder ...
```

dmg까지는 만들어졌는데, 이어지는 pkg 단계의 `pkgbuild`가 한글 헬퍼 앱 경로에서 실패했습니다. arm64 하나만 빌드해도 똑같아서 universal 때문은 아니었습니다.

pkg는 빌드 설정에 들어만 있었고 배포에 쓴 적은 없었습니다. 사장님들이 다운로드 메뉴에서 받아 가시던 맥 설치 파일은 zip이었습니다. 쓰지 않는 형식이라 `pkgbuild`가 왜 실패하는지까지 파고들지 않고, pkg를 빌드 타깃에서 뺐습니다. 지금 보면 한글 이름이 말썽을 부린 첫 신호였습니다.

## 앱이 0.45초 만에 꺼졌습니다

dmg가 나오자, 올리기 전에 이상이 없는지 먼저 테스트했습니다. 사장님들이 설치하시는 것처럼 dmg를 연 뒤, Finder 창에서 앱을 응용 프로그램(`/Applications`) 폴더로 끌어다 놓고 실행했습니다. 앱은 0.45초쯤 떠 있다가 꺼졌습니다. 화면 코드가 돌기도 전이라 앱 로그는 없었고, 남은 건 크래시 리포트뿐이었습니다.

```
Exception Type:  EXC_BREAKPOINT (SIGTRAP)
Termination Reason:  Namespace SIGNAL, Code 5, Trace/BPT trap: 5
Thread 0 Crashed:: CrBrowserMain
```

스택 맨 위는 Electron Framework 안쪽의 v8 심볼이었습니다. 앱 코드 쪽에서 찾을 단서는 없었습니다.

### Finder로 끌어다 놓은 앱만 꺼졌습니다

이상한 건 빌드 폴더에 있는 앱은 멀쩡하다는 점이었습니다. 터미널에서 `cp`로 복사한 앱도 멀쩡했습니다. `/Applications`에 Finder로 끌어다 놓은 앱만 꺼졌습니다. 파일 118개의 크기, 권한, 링크, 서명을 하나하나 비교해 봤지만 다른 게 없었습니다.

그래서 앱 바깥을 의심했습니다. Finder 복사가 덜 끝났나, 그 경로에서 37일째 돌고 있던 Chromium 프로세스 3개 때문인가, LaunchServices 등록이 꼬였나. 재부팅까지 해 봤지만 전부 아니었습니다.

### 이름의 바이트가 달랐습니다

크기도 권한도 같은데 다를 수 있는 게 하나 남아 있었습니다. 파일 이름입니다. 한글은 같은 글자를 두 가지 형식으로 저장할 수 있습니다.

| 형식 | "사"를 저장하는 방식 | UTF-8 바이트 |
|---|---|---|
| NFC (합쳐진 글자) | U+C0AC | `EC 82 AC` |
| NFD (풀어 쓴 자모) | U+1109, U+1161 | `E1 84 89 E1 85 A1` |

화면에서는 똑같이 보입니다. 바이트를 찍어 보니 빌드 폴더의 앱은 NFC, `/Applications`의 앱은 NFD였습니다.

그런데 이름을 전부 NFD로 바꾼 사본은 멀쩡히 떴습니다. NFD가 범인은 아니었던 거죠.

이름 형식을 바꿔 보는 재현 테스트는 처음에 계속 실패했습니다. APFS에서는 NFC 이름을 NFD로 바로 rename하면 이름이 바뀌지 않고 그대로 남는데, 그걸 모르고 돌렸기 때문입니다. 임시 이름을 한 번 거쳐야 실제로 바뀐다는 걸 알아내기까지 시간을 많이 썼습니다.

### 파일을 하나씩 맞바꿔 봤습니다

앱을 받는 경로도 바꿔 봤습니다. zip을 아카이브 유틸리티로 풀면 정상이고, dmg에서 Finder로 끌어다 놓으면 꺼졌습니다. 이전 배포는 zip이었으니, dmg로 바꾸면서 새로 생긴 문제였습니다.

zip으로 돌아가면 당장은 피할 수 있었습니다. 그래도 다른 맥 앱들처럼, dmg를 열면 뜨는 창에서 앱을 응용 프로그램 폴더로 끌어다 놓기만 하면 설치가 끝나게 하고 싶었습니다. 그래서 원인을 찾아 dmg로 가기로 했습니다.

정상 앱과 꺼지는 앱 사이에서 파일을 `mv`로 하나씩 맞바꿔 가며 어디서 갈리는지 좁혀 갔습니다. `Helper (GPU).app`, 그 안의 `MacOS` 폴더, 마지막엔 실행 파일 하나까지 좁혀졌습니다. `Info.plist`와 `PkgInfo`는 관계가 없었습니다.

마지막으로 파일 내용과 이름 형식을 엇갈려 붙여 봤습니다.

| 파일 내용 | 이름 형식 | 결과 |
|---|---|---|
| 정상 앱의 파일 | NFD | 꺼짐 |
| 꺼지던 앱의 파일 | NFC | 정상 |

파일 내용이 아니라 이름 형식이 원인이었습니다.

### 폴더와 파일의 형식이 섞여 있었습니다

Finder로 끌어다 놓은 앱의 이름을 위치별로 찍어 보면 이렇습니다.

| 위치 | 형식 |
|---|---|
| 최상위 폴더 `사장님앱.app` | NFD |
| 본체 실행 파일 `Contents/MacOS/사장님앱` | NFD |
| 헬퍼 폴더 `사장님앱 Helper (GPU).app` | **NFC** |
| 그 안의 실행 파일 `사장님앱 Helper (GPU)` | NFD |

폴더와 파일이 전부 같은 형식이면 NFC든 NFD든 잘 떴고, 섞이면 꺼졌습니다. `cp`, `ditto`, zip은 원래 형식을 그대로 두니까 섞일 일이 없었던 거고요.

Finder가 왜 폴더와 파일을 다르게 저장하는지는 모릅니다. 결과만 봤습니다. Electron Framework 바이너리 안에 `Unable to find helper app`과 `CFBundleName` 문자열이 있는 걸 보면, 헬퍼 앱을 찾는 단계에서 이름이 맞지 않아 죽는 것 같습니다. 다만 이 문구가 실제 로그에 찍힌 걸 본 적은 없어서, 여기까지는 추측입니다.

### 앱 안쪽 이름만 영문으로 바꿨습니다

사장님이 보는 앱 이름은 한글 그대로 두고, 앱 안쪽 이름만 영문으로 바꾸면 형식이 섞일 일이 없습니다. 패키징 직후에 도는 electron-builder의 `afterPack` 훅에 넣었습니다.

```js
// scripts/afterPack.js (이름은 바꿔 적었습니다)
const ASCII_NAME = "OwnerApp";

exports.default = async function afterPack(context) {
  if (context.electronPlatformName !== "darwin") return;

  const productFilename = context.packager.appInfo.productFilename;
  const contents = path.join(context.appOutDir, `${productFilename}.app`, "Contents");
  const macOSDir = path.join(contents, "MacOS");
  if (fs.existsSync(path.join(macOSDir, ASCII_NAME))) return;

  fs.renameSync(path.join(macOSDir, productFilename), path.join(macOSDir, ASCII_NAME));
  setPlist(path.join(contents, "Info.plist"), "CFBundleExecutable", ASCII_NAME);
  setPlist(path.join(contents, "Info.plist"), "CFBundleName", ASCII_NAME);

  // 헬퍼 앱 4개도 실행 파일, 폴더, Info.plist를 같은 방식으로 바꿉니다
};
```

훅은 칩별 빌드에서 한 번, universal로 합친 뒤에 한 번 더 돌아서, 이미 바뀌어 있으면 건너뛰게 했습니다. `.app` 폴더 이름은 한글로 남겼습니다. 앱 코드가 이 경로로 Chromium을 띄우기 때문입니다.

처음엔 실행 파일과 헬퍼 이름만 바꿨는데 계속 꺼졌습니다. `CFBundleName`까지 바꾸고 나서야 세 번 연속 정상으로 떴습니다. 이게 결정적이었는지 따로 나눠서 확인하지는 않았습니다.

## 이번엔 1.30GB가 됐습니다

크래시를 잡고 나니 이번엔 크기가 문제였습니다. dmg가 1.30GB, 설치하면 3.1GB였습니다. 원래 칩별 zip은 220MB 정도였는데요. 앱 코드를 묶은 `app.asar` 하나가 2.2GB였습니다.

원인은 실행 파일인 Chromium을 CRA의 `public/` 폴더에 넣어 둔 구조였습니다.

```
public/chrome-mac-arm (원본)
 ├─ CRA 빌드: public/ 전체를 build/로 복사
 │    └─ electron-builder: build/**/* 를 app.asar에 포장  → 아무도 실행하지 않는 사본
 └─ extraResources: asar 바깥 Resources/public/으로 복사  → 실제로 실행되는 사본
```

코드는 asar 바깥 경로만 봅니다. asar 안에 들어간 사본은 아무도 안 쓰면서 자리만 차지하고 있었습니다.

처음엔 제외 규칙을 `mac.files`에 넣었는데 `build/` 경로에는 먹지 않았습니다. 최상위 `build.files`로 옮기고 나서야 빠졌습니다.

```json
"build": {
  "files": [
    "!build/chrome-mac-arm/**",
    "!build/chrome-mac-intel/**",
    "!build/chrome-win/**"
  ]
}
```

이 줄은 한 번 지우고 끝나는 게 아니라 빌드할 때마다 걸러 주는 필터입니다. CRA가 빌드할 때마다 `public/`을 다시 복사하니까, 이 줄을 지우면 설치 파일은 다시 커집니다.

asar에서 빠진 양은 약 1.7GB로, Chromium 원본 합계 571MB보다 컸습니다. Chromium 안의 링크가 asar에 들어가면서 실제 파일로 풀린 것 같은데, 거기까지는 따로 보지 않았습니다.

## 결과

| 항목 | 이전 (칩별 zip) | universal, 중복 제거 전 | 최종 |
|---|---|---|---|
| 설치 파일 | 2개 | 1개 | 1개 |
| 다운로드 크기 | 212MB, 227MB | 1.30GB | 546MB |
| 설치 후 용량 | 측정 안 함 | 3.1GB | 약 1.4GB |

1.30GB에서 546MB로 58% 줄었지만, 이번 전환으로 불어난 만큼을 덜어 낸 것일 뿐입니다. 이전 칩별 zip과 비교하면 다운로드는 약 2.5배 커졌습니다. 칩 두 벌을 담았으니까요.

대신 설치 파일은 2개에서 1개가 됐고, 새로 빌드할 때도 명령 한 번이면 됩니다. 사장님은 쓰시는 맥의 칩을 몰라도 됩니다. 11월 4일 운영 배포 뒤로는 다운로드 메뉴의 맥 항목도 하나만 남았습니다.

Apple Silicon 맥에서는 dmg를 끌어다 설치하고, 실행하고, 테스트 매장 연동과 앱 안의 arm용 Chromium이 뜨는 것까지 확인했습니다. Rosetta로는 초기 universal 빌드에서 앱과 intel용 Chromium이 뜨는 것만 봤고, 최종 빌드로는 다시 보지 못했습니다. Intel 맥은 기기가 없어서 설치부터 연동까지 하나도 확인하지 못했습니다.

윈도우 설치 파일에도 같은 중복이 남아 있습니다. 제외 줄을 넣은 테스트 빌드에서 설치 후 용량이 1.38GB에서 1.12GB로 줄었는데, 윈도우 기기에서 연동 테스트를 해야 해서 아직 적용하지 못했습니다.

## 마무리

평소에도 사장님 입장에서 겪을 수 있는 경우를 생각하며 테스트해 왔지만, 이번 일로 그게 왜 필요한지 다시 확인했습니다. 터미널에서 `cp`로 복사한 앱은 멀쩡했으니, 사장님처럼 Finder로 끌어다 놓지 않았다면 이 크래시는 보지 못하고 그대로 배포했을 겁니다. 개발자에게 편한 방법으로 확인하면, 사장님이 실제로 겪을 문제는 놓치기 쉽습니다.

앞으로도 사장님이 앱을 받고, 설치하고, 실행하는 순서 그대로 테스트하려고 합니다. 그래야 에러를 조금이라도 더 줄이고, 사장님이 불편을 겪으시기 전에 문제를 먼저 찾을 수 있습니다.

그리고 화면에서 똑같아 보이는 한글 이름도 이제는 바이트부터 찍어 봅니다. 크기, 권한, 서명이 다 같아도 이름은 다를 수 있었으니까요.
