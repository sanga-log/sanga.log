## 이번엔 응답을 만드는 쪽

저는 프론트엔드 개발자입니다. 지금까지 제 일은 잘 만들어진 API에 요청을 보내고, 내려온 응답을 화면에 그리는 것이었습니다. 그런데 이번엔 그 응답을 만드는 쪽이 저였습니다.

사장님용 솔루션에 광고 구독 상품(지도 마커, 검색 리스팅, 카카오톡 광고)을 새로 붙이게 됐는데, 화면만 만든다고 끝나는 일이 아니었습니다. 구독 API, 결제 결과를 받는 워커, 만료·갱신 배치, 운영 어드민까지 필요했습니다. 회사에 프론트 개발자가 저 하나라 화면은 어차피 제 몫이었고, 어쩌다 보니 이번엔 서버 쪽까지 맡게 됐습니다. 두 달 반 동안 만진 레포만 7개입니다. Kotlin/Spring 5개, Django 어드민 1개, 그리고 원래 제 집인 프론트 1개.

컨트롤러에 엔드포인트를 파고 응답 코드를 직접 정하는데 기분이 묘했습니다. **늘 남이 주던 걸, 제가 저한테 주고 있었으니까요.**

## 그동안의 저: "이거 500 나는데 확인 부탁드려요"

연동하다 에러가 나면 저는 늘 스크린샷을 찍어서 백엔드 개발자분께 보냈습니다. "이거 500 나는데 확인 부탁드려요." 그러면 얼마 뒤 "고쳤어요" 하고 답이 왔습니다.

API가 안에서 어떻게 돌아가는지는 몰라도 됐고, 솔직히 알 생각도 별로 없었습니다. 그러면서도 늘 궁금하긴 했습니다. **첫 연동은 왜 매번 에러가 날까?** (명세서대로 보냈는데!)

이 습관이 얼마나 몸에 배어 있었는지는 이번 작업을 하면서 알았습니다. 테스트하다가 400, 500 에러가 뜨자, 저도 모르게 백엔드 개발자분을 태그하고 "이런 에러가 발생했는데 확인 부탁드립니다"를 쓰고 있었습니다. 잘 적었나~ 하고 다시 읽어 보는데... 그 API, 제 거였습니다. 제가 만든 거요. 😅

조용히 글을 지우고 제가 직접 원인을 찾기 시작했는데, 그게 그렇게 낯설 수가 없었습니다. 늘 에러를 넘기던 쪽이었는데, 이번엔 넘길 데가 없었으니까요.

## 첫 요청부터 404가 났습니다

결론부터 말하면, 이번에도 에러가 났습니다. 제가 만든 API인데도요.

dev 서버에 배포하고 프론트에서 첫 요청을 보냈는데 결과는 404. 컨트롤러에 분명히 매핑했는데? 로컬에선 잘 되던 게 dev에서만 404였습니다.

알고 보니 원인은 제 코드가 아니라 길목에 있었습니다. dev 게이트웨이는 경로에 `v2`가 붙은 요청만 새 서버로 보내고, 나머지는 기존 레거시 서버로 보내고 있었습니다. `v2`를 안 붙인 제 요청은 레거시 서버로 흘러가서, 거기서 "그런 주소 없는데?" 하고 404를 받은 거였죠. 제 서버는 요청을 구경도 못 했습니다 😅

```
// 경로는 예시입니다
before: /api/service/subscribe
after : /api/service/v2/subscribe
```

고친 건 경로에 `v2` 두 글자였습니다.

이 순간 좀 웃음이 났습니다. 예전에 제가 "404 나요" 하고 보냈던 것 중에도 이런 게 분명 있었을 겁니다. 백엔드 개발자분들도 화면 너머에서 저처럼 "어 왜 404지?" 하고 있었겠구나 싶었습니다. 원래 그런 거였습니다. **첫 연동이 깔끔하게 되는 게 오히려 이상한 거였어요.**

그 뒤로도 에러는 꾸준했습니다. 일주일쯤 뒤엔 제 PR을 develop에 머지했더니 dev 서버가 아예 뜨지 않았습니다. 카카오 광고용 지역 목록 API를 새로 만들면서, 먼저 만들어 둔 옛 버전을 지우지 않았던 거였습니다. 같은 주소에 API가 두 개 있으니 Spring이 어느 쪽으로 보낼지 정하지 못하고 `Ambiguous mapping`을 던지며 부팅 단계에서 멈췄습니다. 요청이 실패하는 게 아니라 서버가 아예 안 뜨는 에러도 있다는 걸 이때 처음 알았습니다. 그것도 제가 만든 API끼리 부딪혀서요 🥲

## 결제에는 "아직 모른다"가 있었습니다

"응답 하나 만든다"는 게 이렇게 정할 게 많은 일인 줄 몰랐습니다. 그중 제일 낯설었던 건 결제였습니다.

프론트에서 결제는 늘 "됐다 / 안 됐다" 둘 중 하나였습니다. 그런데 서버에서 보니 그 사이에 "**아직 모른다**"는 시간이 있었습니다.

처음엔 저도 프론트 감각대로 짰습니다. 사장님이 구독을 신청하면 바로 `ACTIVE`로 열었더니, 결제가 실패해도 화면에선 구독 중인 것처럼 보였습니다. 결제는 PG사에 요청을 보내고, 결과는 큐(SQS)를 타고 워커로 나중에 돌아옵니다. 신청하는 순간에는 결제가 될지 안 될지 서버도 모릅니다. 그래서 흐름을 이렇게 바꿨습니다.

![비동기 결제 확정 흐름](/images/async-payment-flow.svg)

이 "아직 모른다"를 화면에서 받는 것도 제 일이었습니다.

- 1초 간격으로 최대 10번 폴링
- 10초 안에 확정이 안 되면 "결제 확인 중" 안내로 전환 (스피너에 갇히지 않게)
- 창을 닫았다 다시 열어도 `PENDING`이면 폴링 재개
- 신청 응답(`PENDING`)은 성공으로 치지 않고, 확정은 폴링 결과로만 판단
- 같은 순간의 두 번째 클릭은 state로 못 막아서 ref로 한 번 더 차단

코드로 보면 이렇습니다.

```ts
// 단순화한 코드
const POLL_INTERVAL_MS = 1000;
const POLL_MAX_ATTEMPTS = 10;

const pollPaymentResult = async () => {
  if (pollingRef.current) return; // 이미 돌고 있으면 또 시작하지 않는다
  pollingRef.current = true;
  try {
    for (let attempt = 0; attempt < POLL_MAX_ATTEMPTS; attempt++) {
      await sleep(POLL_INTERVAL_MS);
      const status = await fetchSubscribeStatus();
      if (status === "ACTIVE" || status === "FAILED") return; // 확정되면 끝
    }
    setPaymentTimedOut(true); // 10초가 지나도 PENDING이면 "결제 확인 중" 안내
  } finally {
    pollingRef.current = false;
  }
};
```

솔직히 프론트만 할 때는 폴링이 늘 불만이었습니다. 결과를 바로 상태값으로 내려주면 되지, 왜 프론트가 몇 번씩 다시 물어봐야 하지? 그런데 직접 짜 보니 바로 줄 수가 없었습니다. 신청 API가 응답하는 순간에는 결제 결과가 아직 PG사에서 큐를 타고 오는 중이라, 서버도 결과를 모릅니다. **결과가 나중에 오는 구조라서, 누군가는 다시 물어봐야 했던 겁니다.**

그래서 지금은 고민의 방향이 바뀌었습니다. "왜 폴링을 해야 하지?"가 아니라 "결과가 오기까지 보통 얼마나 걸리지? 그동안 화면에 뭘 보여 주지?"를 먼저 생각합니다. 몇 초까지는 로딩으로 버티고, 그보다 늦어지면 어떤 안내로 바꿀지. 폴링을 그렇게 싫어하던 사람이 이제는 로딩 화면을 몇 초 보여 줄지 재고 있습니다 ㅋㅋ

물론 한 번에 되진 않았습니다. 며칠 뒤엔 조회 API가 `PENDING`/`FAILED`인데도 회차·쿠폰 정보를 채워서 내려주는 바람에, 프론트가 그걸 보고 "구독 중" 화면을 그려 버렸습니다. 서버도 저, 화면도 저. 누굴 탓할 수도 없었습니다.

리뷰를 받고 고친 것도 있습니다. 결제 요청 메시지는 DB 저장이 커밋된 뒤에 보내야 하는데, 저는 그걸 `TransactionSynchronizationManager`에 직접 등록해서 처리하고 있었습니다. 리뷰를 반영해 예약 쪽 코드와 같은 구조(이벤트를 발행하고 `@TransactionalEventListener(AFTER_COMMIT)` 리스너가 보내는 구조)로 바꿨습니다. 동작은 같아도 팀의 다른 코드와 같은 모양이어야 다음 사람이 읽기 쉽습니다. 프론트에서 컨벤션 맞추는 거랑 똑같은 얘기였습니다.

## 에러가 왜 자주 나는지, 이제 압니다

### 1. 흔적도 없이 실패한 400 — 범인은 저였습니다

특정 매장에서만 광고 구독 신청이 계속 실패했습니다. 이상한 건 주문에도 결제에도 아무 기록이 없었다는 점입니다. 데이터가 아예 안 생겼다는 건 저장하기 전에 막혔다는 뜻이라, 여기서 범위가 확 줄었습니다.

원인은 쿠폰 사용 시간이었습니다. 그 매장은 쿠폰을 자정까지 쓸 수 있게 설정했는데, 화면이 그걸 `24:00:00`으로 보내고 있었습니다. 그런데 서버의 Java `LocalTime`은 `00:00:00`부터 `23:59:59`까지만 받습니다. `24:00:00`은 시간이 아니라서 요청 본문을 읽는 단계에서 바로 400(`HttpMessageNotReadableException`)이 났고, 서비스 로직은 한 줄도 돌지 않았습니다. 시간 제한을 안 건 매장은 멀쩡하니까 특정 사장님만 실패하는 것처럼 보였던 거죠.

그리고 이 `24:00`을 보낸 화면은... 제가 만든 거였습니다. 🙃

```ts
// 화면엔 24:00으로 보여주고, 서버엔 23:59:59로 보낸다
const formTimeToServerTime = (time: string): string =>
  time === "24:00" ? "23:59:59" : `${time}:00`;
```

프론트 시절 제가 받았던 400 중 꽤 많은 게 아마 이런 거였을 겁니다. **값 하나가 서버 입구를 통째로 막습니다.** 데이터는 하나도 안 남기고요.

### 2. 결제는 됐는데 아무 일도 안 일어났습니다

결제 성공 뒤에는 해야 할 일들이 있습니다. 결제 로그 남기기, 슬랙 알림, 구독 활성화. 실패하면 재시도하고, 3번 실패하면 해지합니다. 그런데 이게 전부 안 돌았습니다. 에러도 없이요.

워커의 결제 결과 리스너에는 처리할 주문 타입 목록이 있고, 목록에 없는 타입이면 메시지를 확인(ack)만 하고 조용히 넘깁니다. 문제는 그 목록에 제가 새로 만든 광고 구독 타입을 안 넣었다는 거였습니다.

```kotlin
// 단순화한 코드 (타입 이름은 바꿈)
if (orderTxTypeCd !in listOf(
        "AD_LISTING_LEVEL_3",
        "AD_SEARCH_LEVEL_1",
        // "AD_SUBSCRIBE_MARKER",  ← 이게 없었다
    )
) {
    ack.acknowledge()  // 내 결제 결과도 여기서 조용히 사라짐
    return
}
```

에러가 나면 차라리 낫습니다. 로그라도 남으니까요. **아무 일도 안 일어나는 게 제일 무섭습니다.**

### 3. 순서 하나 때문에 "환불할 결제 내역을 찾을 수 없습니다"

구독 취소는 두 가지를 합니다. 레거시 쪽 구독을 만료시키고, 결제를 환불합니다. 처음엔 만료 → 환불 순서로 짰는데, 결과는 "환불할 결제 내역을 찾을 수 없습니다"였습니다.

환불 대상을 찾을 때 레거시 데이터를 기준으로 찾는 경로가 있는데, 바로 앞 단계에서 그 데이터의 종료일을 어제로 바꿔 버렸으니 못 찾은 거였습니다. 제가 방금 만료시킨 걸 제가 찾고 있었던 거죠.

순서를 바꿔서 환불(외부 호출)을 먼저 하게 했습니다. 그러면 덤으로, 환불이 실패했을 때 만료나 노출 변경이 아예 실행되지 않습니다. 외부 호출은 DB처럼 롤백이 안 되니까요. **실패할 수 있는 걸 앞에 두면 "반쯤 취소된" 상태가 생기지 않습니다.** 반대편에 서 보지 않았으면 몰랐을 것 같습니다.

### 덤: 금액이 1~2원 안 맞는 이유

환불액은 `결제액 − (하루 노출료 × 사용일수) − 쓴 쿠폰 할인액`입니다. 코드는 이렇게 생겼습니다.

```kotlin
val exposureDeductionAmt = paidAmt / 30 * exposureDaysUsed
```

`Int` 나눗셈이라 하루치가 먼저 잘립니다. 예를 들어 50,000원을 내고 3일을 썼다면 하루치 1,666.66...원이 1,666원이 되고, 차감액은 5,000원이 아니라 4,998원이 됩니다. 2원이 더 환불되는 셈이죠.

환불 금액 문의가 왔을 때 이걸 알고 있으니 역산이 딱 맞았습니다. "금액이 미묘하게 안 맞아요"의 정체는 이런 계산 순서일 때가 많겠구나 싶었습니다.

## 프론트로 돌아와서

프론트만 할 때는 에러를 보면 늘 "백엔드에서 왜 이렇게 했을까?"부터 생각했습니다. 응답이 이상하면 서버 쪽 사정이겠거니 하고, 스크린샷을 넘기는 데서 제 일이 끝났습니다.

지금은 제가 먼저 원인을 찾아봅니다. 요청 payload는 뭐였는지, 데이터가 저장됐는지 안 됐는지, 어느 단계에서 막혔는지. 그리고 "고쳐주세요" 대신 "이런 값이 들어가면 이 단계에서 에러가 나는 것 같아요"처럼, **어떤 상황 때문에 에러가 나는지를 같이 알려 드립니다.**

화면을 짤 때도 그렇습니다. 서버가 "아직 모른다"를 줄 수 있다는 걸 알고 나니, 스피너 하나를 그릴 때도 타임아웃은? 새로고침하면? 두 번 누르면? 을 먼저 생각하게 됐습니다.
