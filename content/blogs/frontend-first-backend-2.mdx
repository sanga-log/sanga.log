## 1. 흔적도 없이 실패한 400 — 언제나 그랬듯 범인은 저였습니다 ✌️

오픈하고 나서 영업 담당자에게 연락이 왔습니다. 한 매장 사장님이 광고 구독 신청이 안 된다고 영업팀에 연락을 했고, 그걸 저에게 전해 준 거였습니다. 확인해 보니 그 매장에서만 신청이 계속 실패하고 있었습니다. 이상한 건 주문에도 결제에도 아무 기록이 없었다는 점입니다. 데이터가 아예 안 생겼다는 건 저장하기 전에 막혔다는 뜻이라, 에러를 찾아 나설 범위가 확 줄었습니다.

원인은 쿠폰 사용 시간이었습니다. 그 매장은 쿠폰을 자정까지 쓸 수 있게 설정했는데, 화면이 그걸 `24:00:00`으로 보내고 있었습니다. 그런데 서버의 Java `LocalTime`은 `00:00:00`부터 `23:59:59`까지만 받습니다. `24:00:00`은 시간이 아니라서 요청 본문을 읽는 단계에서 바로 400(`HttpMessageNotReadableException`)이 났고, 서비스 로직은 한 줄도 돌지 않았습니다. 쿠폰 사용 시간을 자정까지로 정한 매장만 실패하니, 그 사장님 혼자만 안 되는 것처럼 보였던 거죠.

그리고 이 `24:00`을 보낸 화면은 제가 만든 거였습니다.

사장님 화면에는 그대로 `24:00`으로 보여 주고, 서버로 보낼 때만 `23:59:59`로 바꿔 보내게 고쳤습니다. 반대로 서버에서 `23:59:59`가 내려오면 화면에서는 다시 `24:00`으로 보여 줍니다. 신규 신청과 쿠폰 등록·수정이 모두 요청을 만드는 함수 하나를 거치고 있어서, 보내는 쪽은 그 한 곳만 고치면 됐습니다.

```ts
// 화면엔 24:00으로 보여 주고, 서버엔 23:59:59로 보낸다
const formTimeToServerTime = (time: string): string =>
  time === "24:00" ? "23:59:59" : `${time}:00`;

// 서버에서 23:59:59가 오면 화면엔 다시 24:00으로
const serverTimeToFormTime = (time: string): string =>
  time.startsWith("23:59:59") ? "24:00" : time.slice(0, 5);
```

## 2. 갱신했더니 쿠폰이 사라졌습니다

광고는 한 달 단위 구독이라, 매달 갱신될 때 새 회차를 만들고 쿠폰도 새로 만듭니다. 그런데 기존 시스템에서 넘어온(이관) 매장들이 처음 갱신되던 날, 갱신된 매장 5곳 모두 새 회차 쿠폰이 0장이었습니다. 갱신 슬랙 알림에도 "쿠폰 : 없음"이 찍혔습니다.

이관 매장은 광고 구독을 자동화하기 전부터 기존 시스템으로 광고를 하던 매장입니다. 출시하면서 기존 구독은 새 구독으로 옮겨졌고, 쓰던 쿠폰도 그대로 연결됐습니다. 문제는 이 쿠폰들이 옛 쿠폰 시스템 방식으로 만들어져 있어서, 새 시스템과 수량을 세는 방식부터 달랐다는 점입니다.

새 시스템 쿠폰은 회차마다 새로 만들어서 "이번 회차에 몇 장"을 세지만, 이관 쿠폰은 옛 시스템 방식대로 "지금까지 몇 장"을 세고 발급 상한도 평생 기준이었습니다. 이관 쿠폰을 새 회차에 그대로 복제하면 평생 상한이 한 달 치 수량이 되어, 쿠폰 예산이 실제보다 훨씬 크게 잡힙니다. 그래서 갱신 로직은 이관 쿠폰을 일부러 복제하지 않았습니다. 이관 쿠폰은 첫 회차까지만 쓰고, 다음 회차부터는 새 시스템 쿠폰으로 넘어가게 하려던 설계였습니다. 그런데 넘어갈 새 쿠폰을 만들어 주는 단계가 없어서, 이관 쿠폰만 있던 매장은 갱신하고 나니 쿠폰이 하나도 남지 않았습니다.

이관 쿠폰은 새로 만들지 않고, 원래 쿠폰을 다음 회차에도 계속 쓰게 고쳤습니다. 발급 종료일을 새 회차가 끝나는 날까지 늘리고, 새 회차에 다시 연결하는 방식입니다. 그런데 코드는 앞으로 돌 갱신에만 적용됩니다. 이미 갱신이 지나간 5곳은 DB에서 발급 종료일을 늘리고 회차 연결을 직접 다시 만들어야 했습니다.

프론트에선 배포하면 끝이었습니다. 새로고침하면 다 새 코드로 도니까요. 서버는 아니었습니다. 이미 저장된 데이터는 배포해도 그대로입니다. 심지어 데이터만 고친다고 끝나는 것도 아니었습니다. 고친 데이터가 다른 곳에서 또 어떻게 꼬일지 모르는 거니까요. 백엔드는 참 어렵습니다...

## 3. 에러 없이 옛 시스템에서 돌고 있던 매장

배포하고 나서 불안했습니다. 그래서 구독 갱신과 결제는 슬랙으로 알림이 오게 해 두고, 매일 슬랙 로그를 보면서 쿠폰 발급과 결제 내역을 DB에서 직접 확인했습니다.

그러다 갱신이 돌았는데 쿠폰도 구독 이력도 보이지 않는 매장을 발견했습니다. 조회해 보니 이 매장은 새 구독으로 옮겨지지 않고 옛 시스템에 그대로 남아 있었습니다. 결제는 멀쩡히 되고 있었는데 새 시스템에는 이 매장의 구독이 아예 없었습니다.

기존 매장을 새 구독으로 옮기는 이관은 출시일인 8월 10일에 한 번만 돌린 작업이었습니다. 그날 옛 시스템에 있던 구독을 하나씩 보고, 옮겨도 되는 것만 옮기는 방식입니다. 한 번 돌리고 나면, 그때 빠진 매장을 다시 찾아 옮겨 주는 과정은 없었습니다.

이관에는 "이관하는 날 끝나는 구독은 옮기지 않는다"는 조건이 있었습니다. 그날 끝나는 구독을 옮기면 새 회차가 만들어지자마자 닫혀 버리기 때문입니다.

그런데 이 매장은 그 무렵 결제가 계속 실패하고 있었습니다. 옛 시스템은 결제가 실패하면 다음 날 다시 결제하려고 종료일을 하루씩 뒤로 미룹니다. 그래서 이관이 돌던 8월 10일에는 이 매장이 "오늘 끝나는 구독"처럼 보였습니다.

```
// 결제일이 7일인 매장
8/7 결제 실패 → 종료일 8/8
8/8 결제 실패 → 종료일 8/9
8/9 결제 실패 → 종료일 8/10   // 8/10 이관이 본 모습
```

결제 재시도도, 이관 조건도 각각은 맞게 동작했습니다. 둘이 하필 같은 날 겹치면서 이 매장이 이관에서 빠진 겁니다.

그 뒤에 이 매장의 결제가 성공했습니다. 결제 배치는 옛 구독과 새 구독을 가리지 않고, 그날이 결제일인 구독을 전부 결제합니다. 이관된 매장은 옛 구독을 꺼 두어서 더 이상 결제되지 않지만, 빠진 매장은 옛 구독이 켜진 채로 남아 있었습니다. 그래서 돈은 옛 구독으로 계속 결제되는데, 새 시스템에는 구독이 없는 상태가 됐습니다.

같은 매장이 더 있는지 찾으려고, 옛 시스템에서 결제가 돌고 있는데 새 구독이 없는 곳을 전부 조회했습니다. 48건이 나왔는데 대부분은 결제 없이 광고 노출만 하는 건이라 처음부터 이관 대상이 아니었고, 실제로 빠진 매장은 7곳이었습니다.

- 2곳은 바로 옮겼습니다.
- 3곳은 말일에 결제하는 매장이라, 결제가 성공한 뒤에 옮기기로 했습니다.
- 2곳은 이용권으로 결제하는 매장이었습니다. 새 구독은 카드 결제만 지원해서 옮기지 못했습니다.

에러가 없으니 알람도 울리지 않았습니다. 백엔드의 에러는 눈에 보이지 않습니다. 조용히... 데이터가 꼬여가고 있을 뿐...

## 4. "100장인데 왜 400장이지?"

선착순 쿠폰은 받은 사람 수로 마감됐습니다. 그런데 손님들이 쿠폰을 받아 두기만 하고 쓰지 않는 경우가 많았습니다. 받아 간 사람만으로 쿠폰이 금방 "마감"되다 보니, 정작 당일에 매장을 이용하면서 바로 쓰려는 손님은 쿠폰을 쓸 수 없었습니다. 안 쓴 쿠폰은 유효기간이 끝나면 수량이 돌아오긴 하지만, 그날 쓰려는 손님에게는 소용이 없었습니다. 결국 사장님들로부터 컴플레인이 들어오기 시작했습니다.

마감 기준을 "받은 사람 수"에서 "실제로 쓴 사람 수"로 바꾸면 당장엔 해결되지만, 장단점이 갈리는 문제였기 때문에 영업팀과 회의해서 결정하기로 했습니다.

|  | 받은 사람 수 기준 | 실제로 쓴 사람 수 기준 |
| --- | --- | --- |
| 장점 | 받아 둔 쿠폰은 무조건 쓸 수 있음 | 받기만 한 손님 때문에 마감되지 않음 |
| 단점 | 다 받아 가면 그날 쓰려는 손님이 못 씀 | 받아 둔 쿠폰이 결제 순간에 막힐 수 있음 |

다른 사장님들께도 이런 불만이 들어온 적이 있는지 물어봤더니 몇 군데가 더 있었습니다. 한 매장만의 일이 아니었기 때문에, 실제로 쓴 사람 수 기준으로 바꾸기로 정했습니다.

기준을 정하고 나니 남은 건 단점이었습니다. 사장님이 쿠폰을 20장으로 정했다고 해 보겠습니다. 받기를 무제한으로 열면, 100명이 받아 가도 쓸 수 있는 건 20명뿐이라 나머지 80명은 쓰려고 해도 결제 순간에 막힙니다. 그렇다고 받기도 20장까지만 열면, 20명이 받아 가는 순간 받기가 닫힙니다. 그중엔 안 쓰는 손님도 있으니 실제로 쓰이는 쿠폰은 20장에 못 미치고, 처음 문제로 돌아갑니다. 그래서 받기에도 한도를 두되, 쓸 수 있는 수량보다 넉넉하게 여는 방법을 생각해 냈고, 이 방식으로 수정 작업을 했습니다.

같은 20장이라면, 실제로 쓸 수 있는 건 20장이고 받을 수 있는 건 그 4배인 80장입니다. 배수는 제가 정했습니다. 처음엔 2배로 하려 했지만, 혹시 모를 경우를 대비해 넉넉하게 4배로 열어 두었습니다. 20장이 다 쓰이면 쿠폰은 마감되고, 더 받을 수도 없습니다.

```
// 사장님이 20장으로 정했을 때
실제로 쓸 수 있는 수량  20   // 다 쓰이면 마감
받을 수 있는 수량       80   // 20 × 4
```

사장님 화면엔 정한 수량만 보이게 했습니다. 4배는 내부 사정이니까요.

그런데 갱신 슬랙 알림을 보다가 깜짝 놀랐습니다. "쿠폰 400장". 100장으로 계약한 매장인데 400장이라니?

원인은 알림이 읽던 숫자에 있었습니다. 쿠폰에는 실제로 쓸 수 있는 수량과 받을 수 있는 수량이 따로 저장돼 있습니다. 갱신 알림은 실사용 기준으로 바꾸기 전에 만든 기능이라, 그때 쿠폰 수량이 들어 있던 받을 수 있는 수량을 읽고 있었습니다. 실사용 기준으로 바꾸면서 그 자리에 4배 숫자가 들어갔는데, 화면만 실제로 쓸 수 있는 수량으로 바꾸고 알림은 놓친 겁니다.

## AI 답도 그대로 믿지 않게 됐습니다

이 작업은 AI와 같이 했습니다. 로그를 읽게 하고, 코드 흐름을 따라가게 하고, 쿼리도 짜게 했습니다. 하지만 운영 DB를 고치는 쿼리만큼은 제가 직접 실행했습니다. AI의 답이 실제와 다른 순간이 있었기 때문입니다.

이관에서 빠진 매장을 처리할 때였습니다. AI는 4곳을 바로 옮길 수 있겠다고 정리해 줬습니다. 그런데 실행하기 전에 결과만 미리 보는 기능으로 확인해 보니, 실제로 옮길 수 있는 건 2곳뿐이었습니다. 나머지 2곳은 이용권으로 결제하는 매장이었습니다.

쿠폰이 언제, 어떻게 만들어졌는지 추적할 때도 비슷했습니다. AI는 데이터만 보고 쿠폰이 자동으로 만들어졌다고 추정했습니다. 회차별로 하나씩 다시 따라가 보니, 사람이 직접 만든 쿠폰이 섞여 있었고 자동으로 만들어진 건 일부였습니다.

AI는 도움이 많이 됐고, 작업하면서 실제로 많이 썼습니다. 그래도 DB를 고치는 일만큼은 데이터를 제 눈으로 직접 보면서 제 손으로 하려고 했습니다. DB는 정말 신중하고 또 신중하게 다뤄야 하니까요.

## 마무리

코드는 배포하면 바뀌지만, 이미 쌓인 데이터는 배포한다고 바뀌지 않습니다. 그래서 이제는 무언가를 고칠 때 앞으로 영향을 받을 기능뿐 아니라, 이미 쌓인 데이터와 예외적인 케이스까지 한 번 더 깊게 생각하게 되었습니다.

프론트는 이슈가 생기면 눈에 보여 에러를 바로 확인할 수 있지만, 백엔드는 데이터가 조용히 누적되는 동안 모르고 있다가, 정말 예상치 못한 지점에서 문제가 터집니다. 광고가 갱신된 날 쿠폰이 0장이 돼 버린 매장들처럼, 제가 알아차리기도 전에 사장님들께 불편을 드린 일도 있었습니다. 그 뒤로는 데이터와 로그를 주기적으로 확인합니다. 처음부터 끝까지 제가 만든 거라 계속 신경이 쓰여서, 오늘도 들여다보고 있습니다.
