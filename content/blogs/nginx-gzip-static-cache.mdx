## 시작은 AWS 비용이었습니다

사장님 웹은 브라우저로도 열고, 매장 PC에 설치하는 일렉트론 앱도 같은 주소를 띄웁니다.

올해 9월, 동료 백엔드 개발자가 AWS 비용을 분석하다가 이 서비스를 짚어 줬습니다. 사장님 웹이 접속할 때마다 7.5MB를 다시 내려보내고 있다는 내용이었습니다. 이 서비스는 빌드된 정적 파일만 내보내고 API는 다른 서버가 처리합니다. 그런데 CloudWatch로 다시 보니 8월 한 달 동안 이 서비스의 ALB(로드 밸런서)가 처리한 데이터가 9.5TB였습니다.

설정안도 함께 받아서, 저는 프론트 레포에서 내용을 확인하고 개발 서버와 운영에 적용한 뒤 효과를 쟀습니다.

---

## 매번 7.5MB를 처음부터 받고 있었습니다

원인은 스무 줄짜리 nginx 설정 파일에 있었습니다.

```nginx
server {
    listen 80;

    location / {
        root   /usr/share/nginx/html;
        index  index.html index.htm;
        try_files $uri $uri/ /index.html;

        add_header Cache-Control "private, no-cache, no-store, must-revalidate";
        add_header Expires -1;
        add_header Pragma no-cache;
        add_header Last-Modified $date_gmt;
    }
}
```

문제는 두 가지였습니다.

- `location /` 하나가 모든 요청을 받고 있어서, 이름에 해시가 붙은 JS와 CSS까지 전부 `no-store`였습니다. `no-store`는 응답을 어떤 캐시에도 저장하지 말라는 뜻입니다.
- gzip 설정이 한 줄도 없었습니다. nginx의 `gzip` 기본값은 `off`라서 모든 파일이 압축 없이 나갔습니다.

배포 전에 개발 서버에서 첫 화면의 JS 파일 두 개를 재 봤습니다.

| 파일 | 크기 | 압축 | 캐시 |
| --- | ---: | --- | --- |
| `main.bd7daf2e.chunk.js` | 3,161,677 B | 없음 | `no-store` |
| `12.e29223bf.chunk.js` | 4,364,128 B | 없음 | `no-store` |
| **합계** | **7,525,805 B** | | |

어제 받은 것과 똑같은 7.5MB를 오늘도 처음부터 받고 있었습니다.

## 1년 캐시를 걸어도 되는 이유

정적 파일에 1년 캐시를 건다고 하면 먼저 드는 걱정은 이것입니다. 새로 배포해도 사장님 화면에 옛날 버전이 남는 것 아닐까요?

파일 이름을 보면 답이 나옵니다. `main.bd7daf2e.chunk.js`의 가운데 값은 파일 내용으로 만든 해시입니다. 내용이 바뀌면 이름이 바뀌고, 브라우저는 처음 보는 파일로 여겨 새로 받습니다. 새 이름은 `index.html`이 알려 주니까, `index.html`만 매번 새로 받으면 됩니다.

그래서 파일을 세 묶음으로 나눴습니다.

| 대상 | 캐시 | 이유 |
| --- | --- | --- |
| `/static/` 아래 해시 파일 | 1년, `immutable` | 내용이 바뀌면 이름도 바뀜 |
| `index.html`과 SPA 폴백 | `no-store` 유지 | 새 파일 이름을 알려 주는 파일 |
| `reset.css`처럼 해시 없는 루트 파일 | `no-store` 유지 | 내용이 바뀌어도 이름이 그대로 |

여기서 1년은 사실상 다음 배포까지입니다. 내용이 바뀐 파일은 배포 뒤 한 번은 새로 받습니다. `immutable`은 파일이 신선한 동안에는 새로고침에서도 서버에 다시 확인하지 말라는 표시입니다.

## 바꾼 설정

앱 코드는 고치지 않았습니다. 설정 파일 하나에 gzip 네 줄과 `/static/` 블록 네 줄을 더했습니다.

```nginx
server {
    listen 80;

    gzip on;
    gzip_vary on;
    gzip_min_length 1024;
    gzip_types application/javascript text/javascript text/css application/json image/svg+xml text/plain;

    location /static/ {
        root   /usr/share/nginx/html;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    location / {
        # 기존 설정 그대로
    }
}
```

적용하면서 정한 것은 세 가지입니다.

| 결정 | 이유 | 감수한 것 |
| --- | --- | --- |
| 압축 레벨을 기본값 1로 둠 | 레벨 6은 JS 기준 72.5% 대신 77.4%까지 줄지만 CPU를 더 씀 | 전송량 약 5%p |
| CDN 없이 nginx 설정만 변경 | 받은 제안의 범위였고, 설정 파일 하나로 끝남 | 첫 방문 전송량은 그대로 nginx가 부담 |
| `/static/`에 폴백을 두지 않음 | 없는 해시 파일을 `index.html`로 돌려주면 원인이 가려짐 | 없는 파일 요청이 200에서 404로 바뀜 |

## 없어도 됐던 한 단어

`gzip_types`를 보면 `text/javascript`가 있습니다. 처음 받은 설정안에는 없었고 제가 더한 단어입니다.

적용 전에 nginx의 `.js` 타입을 확인했더니 `application/javascript`였습니다. 받은 설정안대로 해도 JS는 압축됩니다. 다만 RFC 9239는 `text/javascript`를 표준으로 두고 `application/javascript`를 폐기 표시했습니다. 저희 베이스 이미지는 `nginx:latest`입니다. 언젠가 nginx가 매핑을 바꾸면 에러 없이 압축만 멈출 수 있겠다고 보고 한 단어를 더했고, PR에도 그렇게 적었습니다.

그런데 PR 설명을 다시 읽어 보니 이상했습니다. 지금 운영 응답이 `application/javascript`인데 왜 바뀐다고 썼을까요. 근거를 찾아보니 그 변경은 nginx에 PR로 올라왔다가 2025년 12월에 머지되지 않고 닫힌 건이었습니다. `mime.types` 파일을 사실상 동결 상태로 본다는 코멘트도 남아 있었습니다. 지금 운영 응답도 그대로 `application/javascript`입니다.

곧 바뀔 수 있다는 제 근거는 약했습니다. 이 단어가 없어도 압축은 됩니다. 다만 목록에 타입을 하나 더 적어도 nginx가 경고를 내거나 요청마다 비용이 늘지는 않는 것을 소스에서 확인해서, 지우지 않고 남겼습니다.

실제로 챙길 것은 MIME 타입보다 `nginx:latest` 쪽이었습니다. 빌드할 때마다 nginx 버전이 달라질 수 있습니다. 실제로 응답 헤더의 nginx 버전이 9월과 11월에 달랐습니다.

## 개발 서버에서 먼저 확인했습니다

배포 전에 통과 기준부터 적었습니다.

- JS 응답에 `content-encoding: gzip`, `vary: Accept-Encoding`, `cache-control: public, max-age=31536000, immutable`이 모두 있을 것
- `index.html`은 기존 `no-store`를 유지할 것
- 같은 브라우저에서 다시 새로고침하면 `/static/` 파일의 전송량이 0이 될 것

헤더를 볼 때 `curl -I`는 쓰면 안 됩니다. HEAD 요청은 본문이 없어서 nginx의 gzip 필터가 건너뜁니다. 설정이 맞아도 `content-encoding: gzip`이 보이지 않습니다. 그래서 GET을 보내고 본문만 버렸습니다.

```bash
curl -sS -D - -o /dev/null -H 'Accept-Encoding: gzip' \
  -w 'wire_bytes=%{size_download}\n' \
  "https://<도메인>/static/js/<파일명>.chunk.js"
```

개발 서버 배포 뒤 같은 브라우저 탭에서 새로고침을 두 번 했습니다. 첫 번째는 압축을, 두 번째는 캐시를 확인하는 측정입니다.

| 파일 | 전 | 첫 번째 새로고침 | 변화 | 두 번째 새로고침 |
| --- | ---: | ---: | ---: | ---: |
| `main` JS | 3,161,677 B | 770,270 B | −75.6% | 0 B |
| `12` JS | 4,364,128 B | 1,295,538 B | −70.3% | 0 B |
| **합계** | **7,525,805 B** | **2,065,808 B** | **−72.5%** | **0 B** |

`index.html`은 두 번째 새로고침에서도 다시 받아 왔습니다. 의도한 그대로입니다.

응답 시간도 줄어든 것처럼 보였지만 성과로 쓰지는 않았습니다. 전과 후를 한 번씩만 잰 값이라 네트워크 상태의 차이를 가려낼 수 없었습니다.

## 운영에서는 5분 안에 꺾였습니다

9월 17일 16시 51분에 이 설정이 들어간 릴리스를 master에 머지했고, 16시 59분에 ALB가 새 버전으로 트래픽을 넘겼습니다. 아래 그래프는 ALB의 일별 처리량입니다.

![사장님 웹 ALB 일별 처리량 그래프. 9월 17일 이후 약 290GB에서 약 25GB로 줄어듦](/images/nginx-alb-daily-bytes.svg)

5분 단위로 보면 꺾인 시점이 더 분명합니다.

| 시작 시각 (KST) | 처리량 | 요청 수 | 요청당 크기 |
| --- | ---: | ---: | ---: |
| 16:50 | 1,096MB | 891 | 1,231KB |
| 16:55 | 1,085MB | 905 | 1,199KB |
| 17:00 | 304MB | 972 | 313KB |
| 17:05 | 151MB | 609 | 247KB |
| 17:10 | 201MB | 1,194 | 168KB |

전환 전 16시 30분부터 55분까지와 전환 뒤 17시 5분부터 25분까지의 5분 평균을 비교하면 처리량은 −84%, 요청 수는 −14%입니다. 쓰는 사람이 줄었다면 둘이 같이 줄었을 텐데, 처리량만 크게 줄었습니다. 응답이 작아졌다는 뜻입니다.

기간으로 비교한 결과는 이렇습니다. 이 글에서 전송량이라고 부른 값은 CloudWatch의 `ProcessedBytes`입니다. ALB가 처리한 헤더와 본문의 바이트 수이고, 인터넷으로 나간 바이트와 같은 값은 아닙니다. 국내 ALB 하나의 수치입니다.

| 지표 | 배포 전 일평균 (9/8~16) | 배포 후 일평균 (10/1~30) | 변화 |
| --- | ---: | ---: | ---: |
| 처리량 (`ProcessedBytes`) | 290.2GB | 25.3GB | **−91.3%** |
| 요청 수 (`RequestCount`) | 275,022건 | 143,251건 | **−47.9%** |

전송량은 기준을 바꿔도 거의 같습니다. 8월 전체와 비교해도 −91.8%입니다.

요청 수는 다릅니다. 기준 구간 안의 9월 10일 새벽 4시에 한 시간 동안 33만 건이 몰렸고, 그날 하루가 56만 건이었습니다. 다른 날은 23만~26만 건 수준입니다. 이 하루를 빼면 기준은 238,727건이고 감소폭은 −40.0%입니다. 8월 전체 기준으로는 −43.7%입니다. 그래서 요청 수는 −48%보다 40%대 초반의 감소로 읽는 편이 정확합니다. 9월 초에도 요청이 몇 시간씩 몰린 날이 있었습니다. 처리량은 평소 수준이었고 원인은 확인하지 못했습니다. 짧게 몰리는 모양이라 자동화된 요청으로 보이지만 추측입니다.

요청 수가 전송량만큼 줄지 않은 것은 이상하지 않습니다. `index.html`과 해시 없는 루트 파일은 여전히 매번 요청합니다. 다만 경로별 요청을 로그로 나눠 보지는 않아서, 요청이 줄어든 이유가 정적 파일 캐시라는 것도 추측입니다.

## 이 숫자를 어디까지 믿을 수 있을까

같은 시기에 다른 이유로 트래픽이 줄었을 수도 있어서 네 가지를 확인했습니다.

- **시점**: 트래픽이 넘어간 16시 59분 직후에 꺾였습니다. 같은 방식으로 배포했지만 gzip이 없던 9월 16일과 17일 오전의 전환 때는 꺾이지 않았습니다. 같은 시간대에 API를 받는 다른 ALB의 처리량도 시간당 3.19GB에서 3.22GB로 그대로였습니다.
- **사용량**: 그 ALB의 일평균 요청 수는 같은 두 기간 사이에 +0.1%였습니다. 회사 전체 API라 사장님 웹의 사용량 자체는 아니지만, 서비스 이용이 줄어든 흔적은 없었습니다.
- **인프라 변경**: 9월 14일부터 18일까지 CloudTrail을 찾아봤습니다. 배포 전환 말고 이 ALB의 규칙을 바꾼 기록은 없었고, 공개 도메인 DNS와 CDN을 바꾼 기록도 없었습니다.
- **같은 배포의 다른 변경**: 기능 변경이 함께 나갔지만 정적 파일 크기를 크게 바꿀 변경은 찾지 못했습니다. 지금 운영의 첫 화면 JS 두 개도 원본 7.41MB, gzip 2.04MB로 9월 측정과 비슷합니다.

그래서 이 감소의 대부분은 이번 설정의 효과로 보고 있습니다. 비용도 빌링에서 확인했습니다. 이 ALB에 붙는 비용이 처리량과 같은 시기에 줄었고, 변경이 한 달 내내 반영된 첫 달은 10월입니다. 전송비만 따로 뗀 값이 아니라 ALB 항목 전체 기준이고, 구체 금액은 적지 않았습니다.

그래도 확인하지 못한 것이 있습니다.

- **gzip과 캐시의 몫**: 한 번에 배포해서 나눠 재지 못했습니다. 압축률 72.5%만 적용하면 290GB는 약 80GB가 됩니다. 실제로는 25GB까지 줄었으니 그 차이는 캐시 몫으로 보입니다. 어디까지나 어림셈이고 추측입니다.
- **체감 속도**: 운영에서 로딩 시간을 반복 측정하지 않았습니다. 빨라졌을 가능성은 높지만 얼마나 빨라졌는지는 말할 수 없습니다.

## 새벽에도 시간당 5GB가 나가던 이유는 아직 모릅니다

시간대별로 나눠 보다가 궁금한 점이 하나 남았습니다. 배포 전에는 새벽 3시에서 5시 사이에도 시간당 5.66GB가 나갔습니다. 낮 시간대의 13.9GB와 비교해도 적지 않은 양입니다.

| 시간대 | 배포 전 시간당 평균 | 배포 후 시간당 평균 | 변화 |
| --- | ---: | ---: | ---: |
| 03~05시 | 5.66GB | 0.08GB | −98.6% |
| 12~14시 | 13.92GB | 1.42GB | −89.8% |

새벽 값은 9월 10일을 뺀 평균입니다. 낮보다 새벽이 더 크게 줄었습니다. 사람이 적은 시간에 같은 파일을 반복해서 받는 무언가가 있었다는 신호로 보입니다.

코드에서 찾은 후보는 화면 잠금입니다. 잠금 상태에서는 5분마다 페이지를 새로고침합니다. 잠금 상태는 `localStorage`에 남아서 새로고침 뒤에도 타이머가 다시 돕니다. 잠긴 PC 한 대가 하루에 288번 새로고침한다면, 예전 설정에서는 JS만 약 2.2GB를 받게 됩니다.

다만 잠금 상태는 기기에만 저장돼서 몇 대가 켜 두었는지 집계할 수 없었고, 밤에도 운영하는 매장의 정상 사용일 수도 있습니다. 이 항목은 추측입니다.

## 다시 한다면

- **gzip과 캐시를 나눠 배포했을 것입니다.** 하루 차이만 뒀어도 각각의 효과를 잴 수 있었습니다.
- **비교 구간을 배포 전에 정했을 것입니다.** 이번에는 배포 뒤에 구간을 골랐고, 튀는 하루가 섞인 것을 나중에야 봤습니다. 평균과 함께 중앙값도 같이 봤어야 했습니다.
- **운영 전환 직후에 헤더와 지표를 확인했을 것입니다.** 개발 서버까지는 기준을 세워 확인했지만, 기록으로 남은 첫 운영 수치는 10월 말에 뽑은 값입니다.
- **ALB 액세스 로그를 봤을 것입니다.** 남은 하루 25GB가 어떤 파일인지, 새벽 트래픽이 어떤 기기에서 오는지는 로그가 있어야 답할 수 있습니다.
- **`nginx:latest`를 특정 버전으로 고정하자고 제안했을 것입니다.** 버전 선정과 보안 패치를 누가 맡을지 정해야 해서 이번 변경에는 넣지 않았습니다.

이번 설정 변경에서 앱 코드는 한 줄도 고치지 않았습니다. 그래도 사장님 PC로 내려가는 파일의 양은 크게 달라졌습니다. 프론트엔드의 성능 문제가 빌드 결과물을 내보내는 설정에 있을 수도 있다는 것을 이번에 배웠습니다.
