## 시작은 AWS 비용이었습니다

9월에 AWS 인프라 비용을 줄일 방법을 찾던 동료 백엔드 개발자가, 사장님 웹의 nginx 설정만 바꿔도 비용을 줄일 수 있다며 검토를 부탁했습니다. 접속할 때마다 JS 파일 7.5MB를 압축 없이 다시 내려보내고, 캐시도 전혀 걸리지 않는다는 내용이었습니다.

8월 한 달 동안 사장님 웹의 로드 밸런서(ALB)가 처리한 데이터는 9.5TB였습니다. 사장님 웹 서버는 빌드된 정적 파일만 내보내고, API 요청은 다른 서버가 따로 받습니다. 매장 PC에 설치된 Electron 앱도 같은 주소로 화면을 띄우지만, 그걸 감안해도 정적 파일만 내보내는 서버치고는 너무 많은 양이었습니다.

저는 짚어 준 문제가 실제로 맞는지부터 검토했습니다. 프론트 레포의 설정을 점검하고 개발 서버에서 테스트한 뒤, 운영에 적용하고 효과를 쟀습니다.

---

## 매번 7.5MB를 처음부터 받고 있었습니다

nginx 설정 파일을 열어 보니 스무 줄이 전부였습니다.

```nginx
server {
    listen 80;

    location / {
        root   /usr/share/nginx/html;
        index  index.html index.htm;
        try_files $uri $uri/ /index.html;

        add_header Cache-Control "private, no-cache, no-store, must-revalidate";
        add_header Expires -1;
        add_header Pragma no-cache;
        add_header Last-Modified $date_gmt;
    }
}
```

문제는 두 가지였습니다. 먼저 `location /` 하나가 모든 요청을 받고 있어서, 이름에 해시가 붙은 JS와 CSS까지 전부 `no-store`였습니다. 어떤 캐시에도 저장하지 말라는 뜻입니다. 그리고 gzip 설정이 한 줄도 없었습니다. nginx는 gzip이 기본으로 꺼져 있기 때문에, 설정을 해 두지 않으면 모든 파일이 압축 없이 나가게 됩니다.

실제로 개발 서버에서 첫 화면의 JS 파일 두 개를 측정해 보았습니다.

| 파일 | 크기 | 압축 | 캐시 |
| --- | ---: | --- | --- |
| `main.bd7daf2e.chunk.js` | 3,161,677 B | 없음 | `no-store` |
| `12.e29223bf.chunk.js` | 4,364,128 B | 없음 | `no-store` |
| **합계** | **7,525,805 B** | | |

두 파일을 합치면 7.5MB였습니다. 새로고침을 해 봐도 두 파일을 매번 처음부터 다시 받아 왔습니다. 사장님 웹을 열 때마다 7.5MB씩 계속 내려받고 있었던 겁니다.

---

## 1년 캐시를 걸어도 될까

정적 파일에 1년 캐시를 건다고 하면 먼저 이런 걱정이 듭니다. 새로 배포했는데 사장님 화면에 옛날 버전이 남아 있으면 어떡하지?

걱정하지 않아도 되는 이유는 파일 이름에 있습니다. `main.bd7daf2e.chunk.js`의 가운데 값은 파일 내용으로 만든 해시입니다. 내용이 바뀌면 이름이 바뀌고, 브라우저는 처음 보는 파일이니 새로 받습니다. 새 파일 이름은 빌드할 때 `index.html`의 `<script>` 태그에 적힙니다. 브라우저는 `index.html`을 먼저 받고 거기 적힌 이름대로 JS를 요청하니까, `index.html`만 매번 새로 받으면 항상 최신 파일을 받게 됩니다.

그래서 해시가 붙은 `/static/` 아래 파일에만 1년 캐시와 `immutable`을 걸었습니다. `immutable`은 새로고침해도 서버에 다시 묻지 말라는 표시입니다. `index.html`과, `reset.css`처럼 해시 없이 이름이 그대로인 루트 파일은 지금처럼 `no-store`로 뒀습니다. 1년이라고 해도 실제로는 다음 배포까지입니다.

---

## 바꾼 설정

설정 파일에 gzip 네 줄과 `/static/` 블록 네 줄, 모두 여덟 줄을 더했습니다.

```nginx
server {
    listen 80;

    gzip on;
    gzip_vary on;
    gzip_min_length 1024;
    gzip_types application/javascript text/javascript text/css application/json image/svg+xml text/plain;

    location /static/ {
        root   /usr/share/nginx/html;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    location / {
        # 기존 설정 그대로
    }
}
```

위 설정에는 압축 레벨을 정하는 `gzip_comp_level` 줄이 없습니다. 레벨은 1부터 9까지이고, 높을수록 더 작게 줄이는 대신 CPU를 더 씁니다. 이 줄을 쓰지 않으면 nginx는 레벨 1로 압축합니다. 배포 전에 같은 JS 두 파일로 계산해 보니 레벨 1은 72.5%, 레벨 6은 77.4%가 줄었습니다. nginx는 응답을 보낼 때마다 그 자리에서 압축하므로, 5%p를 더 얻으려고 CPU를 더 쓸 이유는 없다고 보고 1로 뒀습니다.

## 개발 서버에서 먼저 확인했습니다

배포 전에 통과 기준부터 정했습니다. JS 응답에 gzip과 1년 캐시 헤더가 붙을 것, `index.html`은 그대로 `no-store`일 것, 같은 브라우저에서 다시 새로고침하면 `/static/` 파일 전송량이 0이 될 것.

개발 서버에 배포하고 개발자 도구 네트워크 탭을 연 채 같은 탭에서 새로고침을 두 번 했습니다. 첫 번째에는 JS 응답 헤더에 `content-encoding: gzip`과 1년 캐시가 붙었는지, 크기가 얼마나 줄었는지 봤습니다. 두 번째에는 `/static/` 파일을 다시 받지 않는지 봤습니다. 네트워크 탭의 캐시 사용 중지(Disable cache)는 꺼 두었습니다. 켜 두면 두 번째 새로고침에서도 파일을 다시 받아 와서 캐시가 걸렸는지 알 수 없습니다.

| 파일 | 전 | 첫 번째 새로고침 | 변화 | 두 번째 새로고침 |
| --- | ---: | ---: | ---: | ---: |
| `main` JS | 3,161,677 B | 770,270 B | −75.6% | 0 B |
| `12` JS | 4,364,128 B | 1,295,538 B | −70.3% | 0 B |
| **합계** | **7,525,805 B** | **2,065,808 B** | **−72.5%** | **0 B** |

`index.html`은 두 번째에도 새로 받아 왔습니다. 의도한 그대로입니다.

## 운영에서는 5분 만에 꺾였습니다

9월 17일 16시 51분에 이 설정이 들어간 릴리스를 master에 머지했고, 16시 59분에 새 버전으로 트래픽이 넘어갔습니다. 아래 숫자는 CloudWatch의 ALB 지표로, 처리량은 `ProcessedBytes`, 요청 수는 `RequestCount`입니다.

![사장님 웹 ALB 일별 처리량 그래프. 9월 17일 이후 약 290GB에서 약 25GB로 줄어듦](/images/nginx-alb-daily-bytes.svg)

5분 단위로 보면 꺾인 순간이 보입니다.

| 시작 시각 (KST) | 처리량 | 요청 수 | 요청당 크기 |
| --- | ---: | ---: | ---: |
| 16:50 | 1,096MB | 891 | 1,231KB |
| 16:55 | 1,085MB | 905 | 1,199KB |
| 17:00 | 304MB | 972 | 313KB |
| 17:05 | 151MB | 609 | 247KB |
| 17:10 | 201MB | 1,194 | 168KB |

전환 전후 25분씩 평균을 내 보면 처리량은 84% 줄었는데 요청 수는 14%만 줄었습니다. 쓰는 사람이 줄었다면 요청 수도 같이 줄었어야 합니다. 줄어든 건 요청 하나에 실려 나가는 양으로, 1.2MB에서 0.24MB로 내려갔습니다.

액세스 로그로 나눠 보면 거의 전부 JS였습니다. 전환 전에는 JS가 요청의 41%였지만 나간 양의 99%를 차지했습니다. 전환 뒤 25분 동안 JS 요청은 31% 줄었습니다. 한 번 받은 JS를 캐시에서 꺼내 쓰는 화면이 생겼기 때문입니다. 새로 받아 간 JS도 한 번에 평균 2.96MB에서 0.69MB로 작아졌습니다. 아직 새 JS를 한 번도 받지 않은 화면이 많은 때라, 이 25분 동안 줄어든 양은 대부분 압축 덕입니다.

기간으로 보면 하루 평균 처리량이 배포 전 9일(9월 8~16일) 290.2GB에서 10월 25.3GB로 91.3% 줄었습니다. 9월 17일에 배포해서 9월은 전후가 섞여 있으니, 설정이 한 달 내내 적용된 첫 달인 10월과 비교했습니다.

## 정말 이 설정 덕분일까

숫자가 너무 크게 줄어서, 같은 시기에 다른 이유로 트래픽이 준 건 아닌지도 봤습니다.

꺾인 시점은 새 버전으로 넘어간 16시 59분 직후였습니다. gzip 없이 같은 방식으로 배포했던 9월 16일과 17일 오전에는 꺾이지 않았습니다. 같은 시간대에 API를 받는 다른 ALB는 시간당 3.19GB에서 3.22GB로 그대로였고, 그쪽 일평균 요청 수도 두 기간 사이에 +0.6%였습니다. 9월 14일부터 18일까지 이 ALB 규칙이나 DNS, CDN을 바꾼 기록도 없었습니다.

그래서 이 감소는 대부분 이번 설정의 효과로 보고 있습니다. 빌링에서도 이 ALB에 붙는 비용이 같은 시기에 함께 줄었습니다.

압축과 캐시가 각각 얼마나 줄였는지는 계산해 볼 수 있습니다. 압축률 72.5%만 적용하면 290GB는 80GB쯤이 됩니다. 실제로는 25GB까지 내려갔으니, 압축하고 남은 양의 3분의 2 이상을 캐시가 덜어 낸 셈입니다. 매장 PC는 이제 화면을 다시 열 때마다 7.5MB를 받는 대신, 다음 배포 전까지 캐시에 있는 JS를 꺼내 씁니다.

## 새벽에도 시간당 5GB가 나가고 있었습니다

시간대별로 나눠 보다가 이상한 걸 하나 발견했습니다. 배포 전 8일 동안, 사람이 거의 없을 새벽 3시에서 5시 사이에도 시간당 평균 5.66GB가 나가고 있었습니다. 낮 12시에서 14시 사이가 13.92GB였으니 적은 양이 아닙니다.

| 시간대 | 배포 전 시간당 평균 | 배포 후 시간당 평균 | 변화 |
| --- | ---: | ---: | ---: |
| 03~05시 | 5.66GB | 0.08GB | −98.6% |
| 12~14시 | 13.92GB | 1.42GB | −89.8% |

새벽이 낮보다 더 크게 줄었습니다. 사람이 없는 시간에 같은 파일을 반복해서 받던 무언가가 있었다는 신호로 봤습니다.

김캐디 사장님을 쓰는 매장 중에는 24시간 돌아가는 무인 매장이 많습니다. 이런 매장은 밤에도 카운터 PC와 키오스크를 켜 둡니다. 코드를 보면 둘 중 페이지를 통째로 다시 여는 건 화면 잠금뿐입니다. 키오스크도 30초마다 예약을 다시 받아 오지만, API 서버로 가는 요청이라 이 ALB를 거치지 않습니다.

화면 잠금을 켜면 화면을 눌러도 반응하지 않고, 5분마다 페이지를 새로고침합니다. 잠금 상태가 `localStorage`에 남아서 새로고침 뒤에도 타이머가 다시 돕니다. 잠긴 PC 한 대가 하루 288번 새로고침하면, 예전 설정에서는 JS만 2.2GB쯤 받게 됩니다.

정말 잠금 때문인지는 ALB 액세스 로그로 확인했습니다. 배포 전 8일 동안 새벽 3시에서 5시 사이 요청을 IP와 브라우저 정보로 묶어 보니, 이 시간에 나간 데이터의 90%가 두 시간 내내 5분마다 페이지를 다시 불러온 화면에서 나왔습니다. 이 화면들은 사장님 PC 앱이나 브라우저로 첫 화면이나 예약 화면을 띄워 둔 매장 PC였고, 키오스크 화면은 없었습니다. 새로고침 간격은 300~306초로, 잠금 타이머 5분에 페이지를 다시 여는 시간이 더해진 값이었습니다. 사람이 쓰는 화면이라면 두 시간 동안 이렇게 일정하게 새로고침할 일이 없습니다.

배포 뒤인 10월 중순에도 새벽마다 같은 간격의 새로고침은 그대로 이어졌습니다. 달라진 건 받는 양입니다. 이제 JS는 캐시에서 꺼내 쓰고 `index.html`과 해시 없는 루트 파일만 새로 받아서, 이 새로고침이 가져가는 양은 시간당 0.01GB 정도로 줄었습니다.

## 마치며

앱 코드는 한 줄도 고치지 않았습니다. 그저 nginx 설정 여덟 줄을 바꿨을 뿐인데, 매장 PC로 내려가는 트래픽이 하루 290GB에서 25GB로, 10분의 1 아래로 줄었습니다. 사용자 수도, 화면을 여는 횟수도 그대로인데 받는 양만 줄어든 것입니다.

다음에 비슷한 작업을 할 때는 gzip 압축과 캐시 설정을 하루 간격으로 나누어 배포해 보려 합니다. 그래야 각 설정이 트래픽을 얼마나 줄였는지 계산이 아닌 실제 운영 수치로 확인할 수 있을 테니까요.
